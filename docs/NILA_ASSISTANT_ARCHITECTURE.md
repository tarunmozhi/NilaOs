# Nila Assistant — Architecture and Implementation Plan

Status: architecture plus starter Android implementation. This is not a production AI assistant and is not yet integrated into Nila OS.

## Product goals

- Ship as a standalone Android app first; later provide a documented integration boundary for Nila OS.
- Treat Tamil and English as first-class languages. The preferred wake phrase is “Hey Nila”; the preferred casual Tamil response phrase is “சொல்லுங்க மாமா”.
- Local-first by default. Online research and optional remote AI are separate, explicit capabilities.
- The assistant is not a security authority. Every sensitive action is mediated by a deterministic policy layer and the Android permission/user-confirmation flow.
- Do not send passwords, OTPs, access tokens, private account data, or secret-zone content to remote services.
- No Google/Gemini/AICore/Firebase dependency is required by this starter.
- The vivo Y11 / vivo 1906 / PD1930F target has Snapdragon 439 and 3 GB RAM. Keep the UI and core policy lightweight; large models and video generation should run on a capable PC or a separately selected online provider, not be assumed to run locally on this phone.

## Layered architecture

1. **Presentation** — Android Activity initially; later Compose UI, chat history, Tamil/English input, accessibility, voice controls, settings and permission explanations.
2. **Conversation coordinator** — classifies a request into local answer, research, app action, coding, accounting, authorized security lab, media creation, or unsupported action. It must never execute arbitrary model output as a command.
3. **Policy engine** — deterministic rules for data zones, outbound disclosure, user consent, app actions, network destinations and media requests. Fail closed when policy cannot decide.
4. **Privacy boundary** — Public / Private / Secret data labels. Secret data never leaves the device. Private data requires an explicit, scoped disclosure decision. The current starter uses conservative heuristic checks, not a complete DLP classifier.
5. **Local knowledge and memory** — planned SQLite store with user-visible records, retention controls, export/delete controls and source attribution. No persistent chat memory is implemented in the starter.
6. **Local inference adapter** — planned interface for a small on-device model and deterministic intent rules. The starter currently provides only a minimal local help response; it is not an LLM.
7. **Online research gateway** — allowlisted HTTPS source adapters, timeouts, bounded responses, source links and explicit outbound-query screening. The starter queries Wikipedia's public search API only; it is not a general-purpose web crawler and does not call a commercial search API.
8. **Optional remote model adapter** — future provider plug-in behind a user-configured gateway. Redact before network access, never put API keys in source control, and do not expose privileged phone-control APIs to a model.
9. **Action broker** — typed actions such as OpenAppStoreSearch and RequestUninstall. Every operation uses Android system UI. Ordinary apps cannot silently install/uninstall arbitrary apps; device-owner or root-based management would require a separate, security-reviewed helper.
10. **Media adapter** — future provider-neutral interface for image/video generation. The starter includes policy scaffolding only, not a generator. Provider terms and applicable law remain in force.
11. **Audit and diagnostics** — planned local, redacted event log for action requests, consent decisions and failures. Do not log message bodies, secrets, tokens or private prompts by default.
12. **Nila OS bridge** — future narrow IPC contract to Nila services. It must not be a generic shell endpoint. Each privileged operation needs an allowlisted verb, caller authentication, policy evaluation, explicit consent where appropriate and an auditable result.

## Data flow

User input → local classification → data-zone / policy check → one typed route:

- Local response: on-device rules/model only.
- Research: outbound query screening → HTTPS allowlisted source adapter → bounded parse → source-linked results.
- App action: validate package/search input → explain action → Android system confirmation screen.
- Remote inference: only if enabled and consented → redact/block secrets → provider adapter → validate response as untrusted text.
- Media request: validate request metadata → policy decision → provider's own policy checks → explicit preview/confirmation → output stored in user-selected location.

Retrieved webpages, model responses, scripts, APK metadata and prompts are untrusted input. They cannot change policy, grant permissions, invoke tools by themselves or override user confirmation.

## Security invariants

- Never execute shell commands generated by the model.
- Never give the model a raw root shell, Accessibility-service control, or unrestricted Intent launcher.
- Never silently install or uninstall apps in the regular-app profile.
- Do not request broad package visibility unless a documented feature needs it.
- Use HTTPS, connection/read timeouts, response-size limits and strict host allowlists for network adapters.
- Do not persist secret data. Redaction heuristics are defense in depth, not a guarantee.
- Root support, if added later, must be optional, disabled by default, scoped to a reviewed allowlist and confirmed per operation.
- Adult media support, if added, must obey the selected provider's rules and local law. Block sexual content involving minors and non-consensual intimate imagery/deepfakes. Do not build provider-restriction bypasses.
- Keep secrets, signing keys, provider keys and personal data out of GitHub.
- Show users when a capability is only a demo or unavailable.

## Android app management

The starter supports two safe flows:
- Search the Play Store for an app, leaving installation to the user and Play Store UI.
- Request Android's uninstall confirmation for a package ID the user supplies.

This is intentionally not a silent installer. Package names must be verified by the user. Android version, package visibility, store availability and device policy can affect these flows. Local APK installation is not implemented.

## Research scope

The starter uses Wikipedia OpenSearch through HTTPS and shows titles, descriptions and source URLs. It does not crawl arbitrary sites, bypass logins, evade rate limits, or scrape protected content. A future search-provider adapter should add provider selection, rate limits, robots/terms checks where applicable, safe HTML parsing, source ranking, duplicate detection, citations and prompt-injection isolation.

## Media-generation scope

The starter does not generate images or videos. A future adapter should define provider, prompt, content mode, consent/source information, output destination, cost/usage limits and cancellation. Local generation is not realistic to promise on the vivo Y11's 3 GB RAM. Use a capable PC or a compliant provider if/when that module is implemented.

## Roadmap and acceptance criteria

### Phase 1 — Android foundation (this branch)
- Android app shell with a text input and action buttons.
- Minimal local help response.
- Wikipedia search with outbound-query screening and source URLs.
- User-mediated app-store search and uninstall confirmation.
- Unit tests for secret-pattern blocking.
- Architecture and security boundaries documented.

### Phase 2 — Conversation engine
- Add typed request classification, SQLite-backed user-controlled memory, deletion/export and source citations.
- Add an inference interface with deterministic fallback and a separately configurable local model.
- Add Tamil/English language tests and voice input/output behind explicit Android permissions.

### Phase 3 — Research
- Add provider adapters without hard-coded API secrets.
- Add bounded page extraction, canonical URLs, source ranking, duplicate detection, prompt-injection isolation and test fixtures.
- Add request cancellation, rate limiting and privacy review.

### Phase 4 — Tools
- Add coding and accounting tools with sandboxed execution or pure calculations.
- Add authorized cybersecurity lab workflows limited to user-owned or explicitly authorized targets.
- Add app inventory only after Android package-visibility requirements and privacy implications are reviewed.

### Phase 5 — Media and optional privileged helper
- Add a provider-neutral media interface and policy tests; no bypassing provider restrictions.
- If root/device-owner functionality is truly required, design and audit a separate narrow helper before enabling any privileged action.
- Integrate with Nila OS only after the OS has authenticated IPC, enforced isolation and audit support.

### Release gates
- Unit tests and Android build pass in CI.
- No network call occurs for a query blocked by the policy engine.
- App actions only open system-mediated screens.
- Secret-pattern test suite passes.
- Privacy disclosures and retention controls are implemented before remote model support.
- A successful Android build is not proof of installation or operation on vivo 1906; device testing must be recorded separately.
